Заправка в рейсе

1. Расхождения в материалах и принятые решения

1.1. Лимит на рейс

Расхождение. В макете общий лимит составляет 20 000 руб., доступно 12 450 руб. В API для текущего рейса возвращаются 15 000 руб. общего лимита и 9 340 руб. доступного остатка. В разговоре диспетчер говорит, что на весь рейс выделено 20 000 руб., а сейчас водителю доступно около 9 300 руб..

Решение. В прототипе текущие значения общего лимита и доступного остатка берутся из getTrip().

Почему. API является единственным источником актуального состояния рейса, с которым фактически работает прототип. Значения из макета нельзя использовать как данные, а разговор подтверждает, что общий лимит и доступный остаток могут различаться из-за предыдущих заправок и холдов.

1.2. Тягач и прицеп

Расхождение. В макете на главном экране указаны и тягач, и прицеп, однако API возвращает только поле truck и не содержит данных о прицепе.

Решение. В прототипе отображается только тягач.

Почему. Номер прицепа невозможно получить из предоставленного API, поэтому добавлять его в интерфейс означало бы придумывать отсутствующие данные.

1.3. Обозначение колонок

Расхождение. В разговоре водитель видит на самой АЗС буквенные обозначения колонок, а в приложении - числовые. В API колонки также представлены числовыми значениями.

Решение. В прототипе сохранены числовые номера колонок из API и добавлено пояснение, что буквенные обозначения соответствуют им по порядку: А - 1, Б - 2 и далее.

Почему. Менять значения API нельзя, но без пояснения водитель может выбрать не ту колонку. Такое сопоставление прямо следует из разговора с диспетчером.

1.4. Возможность отмены заправки

Расхождение. В разговоре диспетчер говорит, что заказ можно отменить, пока залито не больше половины заказанного объёма. fake-api.js задаёт другие допустимые состояния отмены и не поддерживает это правило в таком виде.

Решение. В прототипе возможность отмены определяется фактическими состояниями, которые поддерживает API.

Почему. Интерфейс не должен обещать водителю действие, которое сервер не сможет выполнить. Для рабочего прототипа поведение API является ограничением.

1.5. Время на установку пистолета

Расхождение. В разговоре диспетчер говорит примерно о 40 секундах на установку пистолета, тогда как API использует тайм-аут 60 секунд.

Решение. В прототипе используется значение 60 секунд, а итоговое состояние заказа определяется ответом API.

Почему. Если интерфейс будет считать заказ отменённым раньше сервера, состояние приложения и состояние заправки разойдутся.

1.6. Чек после заправки

Расхождение. В макете итогового экрана написано «Чек отправлен диспетчеру». В разговоре диспетчер говорит, что чек приходит ей от АЗС позднее по электронной почте и в приложении его нет. API также не подтверждает отправку чека диспетчеру.

Решение. В прототипе используется формулировка: «Чек поступит диспетчеру после обработки заказа АЗС».

Почему. Так интерфейс не сообщает как уже совершившийся факт действие, которое в момент завершения заправки ещё не подтверждено.

1.7. Отдельный бак рефрижератора

Расхождение. В разговоре диспетчер говорит, что бак рефрижератора заправляется отдельным заказом, но в рамках того же общего лимита рейса. При этом API не содержит признака бака или другого объекта заправки.

Решение. В прототипе разные баки оформляются отдельными заказами.

Почему. Это позволяет сохранить описанный диспетчером порядок действий и общий лимит, не расширяя предоставленный API вымышленными полями.

1.8. Изменение цены во время оформления заказа

Расхождение. В разговоре водитель видит на табло АЗС цену 71,70 руб./л, а в приложении — 71,71 руб./л. Диспетчер уточняет, что заказ оформляется по цене приложения, а при её изменении заказ нужно подтвердить заново. API также проверяет актуальность переданной цены и может отклонить заказ при её изменении.

Решение. В прототипе используется цена из API на момент оформления. Если сервер сообщает об изменении цены, приложение обновляет данные и требует повторного подтверждения заказа.

Почему. Цена на физическом табло не является частью предоставленного API, а заказ должен создаваться по той цене, которую сервер способен подтвердить и списать.

1.9. Поведение при потере связи после отправки заказа

Расхождение. Из разговора следует, что при плохой связи водитель может не получить ответ приложения, хотя заказ уже был создан на стороне АЗС. Повторное нажатие в таком случае уже приводило к появлению двойных заказов. Обычная повторная отправка нового запроса поэтому небезопасна.

Решение. В разработанном прототипе повторная попытка создания одного и того же заказа выполняется с тем же clientRequestId, а активный заказ после восстановления связи проверяется через API.

Почему. При сетевой ошибке невозможно надёжно определить по клиентской стороне, был ли первый запрос выполнен. Повтор с тем же идентификатором позволяет получить результат той же операции, не создавая новый заказ.

3. Решение для владельца парка

Выбранная мера

1. Перед оформлением заказа водитель сначала указывает, какой объём топлива ему действительно нужен.
2. После этого приложение предлагает подобрать выгодную АЗС для указанной потребности.
3. В качестве отправной точки показывается ближайшая подходящая АЗС.
4. Рядом с ней водитель видит цену выбранного топлива и стоимость нужного ему объёма.
5. Ниже приложение показывает более выгодные подходящие АЗС.
6. Для каждой альтернативы показываются расстояние, цена и экономия или переплата относительно базового варианта.
7. При ручном выборе АЗС приложение также показывает блок «Можно выгоднее», если найдены более дешёвые варианты.
8. Решение не запрещает водителю заправляться на выбранной АЗС, поскольку приложение не знает всех дорожных обстоятельств.
9. Такой шаг одновременно снижает вероятность выбора дорогой АЗС и заменяет решение «потратить весь доступный лимит» на осознанный выбор требуемого объёма топлива.

Отвергнутые альтернативы:

1) Жёстко запретить заправку на дорогих АЗС.  
От этого варианта я отказался, потому что предоставленных данных недостаточно, чтобы гарантировать доступность более дешёвой АЗС в конкретной дорожной ситуации. Жёсткий запрет может помешать водителю выполнить рейс.

2) Автоматически выбирать АЗС и объём за водителя.
От этого варианта я отказался, потому что для такого решения недостаточно данных о маршруте, фактическом запасе топлива, дорожной ситуации и причинах, по которым водителю может понадобиться конкретная АЗС.

Метрика через месяц, по которой я пойму, что ошибся в выбранном подходе:
Доля заказов, в которых водитель выбрал более дорогую АЗС при наличии показанной ему более дешёвой подходящей альтернативы.
Если через месяц эта доля не снизится по сравнению с периодом до запуска решения, значит подсказка не изменила поведение водителей и выбранная мера оказалась неэффективной.
